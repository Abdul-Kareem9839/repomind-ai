# How RAG Works

RepoMind's core promise is that every answer about a repository is grounded in
that repository's actual code, not the model's general training knowledge. This
is what makes that true, end to end: ingestion (done once per project, at upload
time) and retrieval (done on every chat question).

## Part 1 — Ingestion (upload time)

Triggered by `POST /api/projects/github` or `/api/projects/upload`, run by
`services/project.service.js`, and — in V1 — run **synchronously**: the request
doesn't return until every step below has completed and the project's status is
`ready` (or `failed`).

```
Clone / Extract  →  Parse  →  Analyze  →  Chunk  →  Embed  →  Store (Chroma)
```

### 1. Clone / Extract

- **GitHub**: `services/github/github.service.js` shallow-clones the URL into
  `TEMP_DIR/<projectId>`.
- **ZIP**: `services/parser/zipExtractor.service.js` extracts the upload into the
  same kind of per-project temp directory, then deletes the original `.zip` from
  disk — it's never kept around. If the archive contains one single root folder
  (the common case when someone zips a project folder directly), it's flattened
  so parsing always sees files sitting directly under the workspace root.

### 2. Parse

`services/parser/fileParser.service.js` walks the workspace recursively and
keeps only files that are actually useful for understanding code:

- **Supported**: `.js .jsx .ts .tsx .json .md .html .css .yaml .yml`, plus the
  literal filename `.env.example`
- **Skipped directories**: `node_modules, dist, build, .git, .next, .turbo,
coverage, .cache, out, vendor, __pycache__, .venv`
- **Skipped files**: anything empty or over 400KB (generated/minified/lockfile
  noise), and anything that fails to read as UTF-8 text (binaries that slipped
  past the extension check)

Each surviving file becomes a document: `{ filepath, filename, language,
content, sizeBytes }`.

If zero documents survive this step, ingestion fails immediately with a clear
error rather than proceeding to index nothing.

### 3. Analyze

`services/parser/repositoryAnalyzer.service.js` runs once over all parsed
documents and produces a structured `repositorySummary`, without any LLM call
for the structural parts:

- Reads every `package.json` found and unions their dependency names
- Matches dependency names against known signatures to detect **frameworks**
  (React, Express, Next.js, NestJS, Vue, Angular, Svelte, Fastify), **database**
  (Mongoose/MongoDB, raw `mongodb`, pg, mysql2, Sequelize, Prisma), and
  **auth strategy** (`jsonwebtoken`, `passport`, `next-auth`, `bcrypt`/`bcryptjs`)
- Regex-scans route-registration calls (`app.get(...)`, `router.post(...)`,
  etc.) across all files to build a route table with method, path, and source file
- Files matching `/auth|jwt/i` in their path are collected as auth-related files

The one LLM-backed part is a free-text `summary` paragraph, generated by
`services/ai/gemini.service.js` (`generateText`, not the LangChain-wrapped
model — this call doesn't need prompt composition). If no `GEMINI_API_KEY` is
configured, `generateText` returns `null` and ingestion continues without a
prose summary rather than failing — everything else in `repositorySummary` is
still fully populated.

This structured summary is stored directly on the `Project` document
(`repositorySummary` field) **and** separately turned into a searchable chunk
(next step) — it does double duty as both quick-glance project metadata and the
first thing retrieved for architecture-type questions.

### 4. Chunk

`services/rag/chunker.service.js` deliberately does not chunk by raw character
count. For JS/TS/JSX/TSX files, it splits along **top-level function and class
boundaries** using brace-depth tracking, so a chunk is either:

- a whole top-level `function`/`class` declaration, or
- a "module" block — everything before the first symbol (imports, top-level
  consts, config objects) that would otherwise be lost

Only if a single block still exceeds 6000 characters (e.g. one enormous
generated function) does it fall back to splitting on blank-line boundaries.
Non-code files (`.md`, `.json`, `.css`, `.html`, `.yaml`) are kept as one chunk
per file.

Every chunk carries metadata used later at retrieval time:
`filepath, filename, language, imports, exports, chunkType, symbolName,
chunkIndex`. `imports`/`exports` are extracted from `import`/`require`/`export`
statements and are what let `codeFlowRetrievalNode` (see `docs/LANGGRAPH.md`)
follow a chunk to the files it actually depends on.

On top of the per-file chunks, `services/rag/indexer.service.js` builds one more
document — the **repository summary chunk** — a dense, human-readable rendering
of the whole `repositorySummary` object (frameworks, languages, dependencies,
routes, auth strategy, database, etc). This is what architecture and
documentation questions retrieve first, before falling back to a normal
similarity search.

### 5. Embed

`services/ai/embeddings.service.js` embeds every chunk's text with the
configured local feature-extraction model (`LOCAL_EMBEDDING_MODEL`, default
`Xenova/all-MiniLM-L6-v2`), batching chunks locally using `@xenova/transformers`
instead of calling an external Gemini embedding service. Unlike the analyzer's
summary paragraph, embeddings are **not optional** — `embedTexts` throws
immediately if
the local model cannot be initialized, since without vectors there's nothing to
store or search.

### 6. Store

`services/vector/vectorStore.service.js` upserts the embedded chunks into a
ChromaDB collection dedicated to this project — one collection per project,
named `{CHROMA_COLLECTION_PREFIX}_{projectId}` (see `utils/collectionName.js`),
so projects never share vector space and deleting a project cleanly deletes its
collection. Chroma only accepts string/number/boolean metadata values, so array
fields (`imports`, `exports`) are flattened to comma-joined strings before
upsert.

Once this resolves, `project.status` flips to `ready`, and the temp workspace
from step 1 is deleted — from this point on, the original source is gone; only
what got indexed remains queryable.

## Part 2 — Retrieval (every chat question)

```
Question → Embed → Similarity search (ChromaDB) → Build context → Prompt Gemini → Answer
```

`services/rag/retriever.service.js` exposes the primitives every LangGraph node
builds on:

- **`retrieveChunks({ question, topK, where })`** — embeds the question with the
  same embedding model used at ingestion time, then runs a similarity search
  against the project's collection. `where` is an optional Chroma metadata
  filter (e.g. restrict to `chunkType: 'repository_summary'`); most nodes leave
  it unset for a broad search.
- **`retrieveRepositorySummary()`** — fetches the repository summary chunk
  directly by metadata match, skipping the embedding + similarity search
  entirely, since there's exactly one and its ID is known.
- **`buildContext(chunks)`** — joins retrieved chunks into a single string,
  each prefixed with its filepath, ready to drop into a prompt template.

Which combination of these a question uses depends on its category — that
routing logic is the LangGraph workflow, covered in full in `docs/LANGGRAPH.md`.
The short version: every category retrieves _something_ real from the project's
collection before generating an answer, and `answerNode` always tells the model
explicitly when nothing was retrieved ("No repository context was retrieved for
this question") rather than silently letting it guess.
